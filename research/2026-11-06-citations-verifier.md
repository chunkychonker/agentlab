# Citations, and verifying that a citation is true (2026-11-06)

## Question
How do Claude API citations work on the wire (shapes, indexing, streaming, incompatibilities), and what small, offline-testable increment would make a lab agent's grounded answers checkable?

## Findings
Backlog state: no plain `[ ]` feature item remained (only stale `fix (health ...)` lines and stranded claims), so per the PR #71 precedent I filed a new topic. No open PRs at start (`gh pr list` empty). Tooling note: the `hn-search` MCP server failed to connect this session (missing `examples/mcp-hn-search/.venv/bin/python3`), so no HN practitioner discussion was consulted. A web search turned up nothing 2026-specific on gotchas, so everything below rests on the official page.

Primary source: [Citations docs](https://platform.claude.com/docs/en/build-with-claude/citations) (fetched 2026-11-06; its examples use `anthropic-version: 2026-10-21`). Status stable, all active models supported, including `claude-haiku-4-5` and `claude-sonnet-5-5`.

- Enable per document: `{"type":"document","source":{...},"title":..., "citations":{"enabled":true}}`. Citations must be enabled on all or none of the documents in a request.
- Three document kinds, three citation shapes:
  - Plain text gives `char_location` with `document_index`, `document_title`, `start_char_index`, `end_char_index`. Indices are 0-indexed with an exclusive end. The API chunks the text into sentences.
  - PDF gives `page_location` with `start_page_number` (1-indexed) and `end_page_number` (exclusive).
  - Custom content (a list of content blocks you chunk yourself) gives `content_block_location` with `start_block_index` and `end_block_index` (0-indexed, exclusive end).
  - `document_index` is 0-indexed across all document blocks in the request, spanning all messages.
- Response: several `text` blocks, each with an optional `citations` list. A single claim can carry several citations.
- `cited_text` is extracted by the API, not generated by the model. It is free as output tokens, and also free as input tokens when passed back on later turns. Docs say the pointers are "guaranteed to be valid". Enabling citations still adds a little input from system-prompt additions and chunking.
- Streaming: a `citations_delta` delta type inside `content_block_delta`. Each delta carries ONE citation to append to the current text block's `citations`.
- Works with prompt caching (`cache_control` on the document block), `count_tokens`, and batches.
- Incompatible with structured outputs. Citations on any `document` or `search_result` block plus `output_config.format` (or deprecated `output_format`) returns 400. The docs' workaround is to ask for one line per field and parse it yourself.
- Related breaking change, from [[anthropic-api-2026-10-21]]: non-empty `citations` on a user `text` block, and a `document` block inside an assistant message, both 400 under the new version.

Gap in the claim "guaranteed valid": the guarantee is about the API's parsing. An agent that stores or forwards citations (a cache, a rewritten document, an edited context) can end up with pointers that no longer match the text. A client-side re-check is cheap and pure. I did not verify whether `cited_text` is always an exact slice of the chunked source. That is a good empirical question for the live call, since chunking is sentence-based and could normalise whitespace.

## Build proposal
Directory: `examples/citation-verifier/` (checked: absent from `ls examples/`, no open PRs).

**Intent.** Make "this answer is grounded" checkable by code: re-derive each citation's quoted span from the source document and compare. Out of scope: PDF page verification, `search_result` and web-search citations, structured outputs, a RAG pipeline.

**Behavioral spec.**
- Input: the list of source documents the request used (in request order, as plain text strings or lists of block strings) plus the response `content` as dicts.
- Output: one `Verdict` per citation, with status in `{MATCH, MISMATCH, OUT_OF_RANGE, BAD_DOCUMENT_INDEX, UNVERIFIABLE}`, plus a response-level summary (count by status, and a list of text blocks with zero citations).
- `char_location` is MATCH iff `0 <= start < end <= len(doc)` and `doc[start:end] == cited_text`. Otherwise OUT_OF_RANGE, or MISMATCH when the range is valid but the text differs.
- `content_block_location` is MATCH iff `"".join(blocks[start:end]) == cited_text`, with the same range rules. Whether the join is exact is unconfirmed (see open questions), so the builder should allow only the join variant the live call proves.
- `page_location` is always UNVERIFIABLE (offline, no PDF parser), never silently MATCH.
- `document_index` outside the document list is BAD_DOCUMENT_INDEX.
- Unknown citation `type` is UNVERIFIABLE (no crash). Malformed input (missing field) raises `ValueError` naming the field. Fail loudly, do not default.
- Streaming helper: a pure `accumulate(events)` that rebuilds text blocks from `text_delta` and `citations_delta` events, so a replayed event list yields the same blocks as the non-streaming shape. Event replay uses `SimpleNamespace`/dict fixtures, as in `examples/streaming-tool-loop/`.
- Invariants: the core imports no I/O and no SDK. The CLI edge reads the key and calls `client.messages.create`.

**Interfaces.**
```python
Status = Literal["MATCH","MISMATCH","OUT_OF_RANGE","BAD_DOCUMENT_INDEX","UNVERIFIABLE"]
@dataclass(frozen=True) class Verdict: block_index:int; citation_index:int; status:Status; detail:str
def verify_response(documents: Sequence[str | Sequence[str]], content: Sequence[dict]) -> list[Verdict]
def uncited_text_blocks(content: Sequence[dict]) -> list[int]
def accumulate(events: Iterable[dict]) -> list[dict]
```
Files: `verifier.py` (core), `stream.py` (accumulator), `live_demo.py` (edge, one call on `claude-haiku-4-5`, a 3-sentence plain doc and one custom-content doc, asserts all MATCH and prints a table), `test_verifier.py`, `requirements.txt` (`anthropic>=2` is acceptable, but pin a floor of the version actually tested), `README.md`.

**Acceptance criteria (self-test, offline, no key).**
1. A hand-built `char_location` fixture matching `doc[start:end]` gives MATCH.
2. Same fixture with `cited_text` altered gives MISMATCH. With `end` past `len(doc)` it gives OUT_OF_RANGE. With `start == end` it gives OUT_OF_RANGE (the end is exclusive, so an empty span is invalid).
3. `document_index=2` with two documents gives BAD_DOCUMENT_INDEX.
4. `content_block_location` fixtures give MATCH and MISMATCH correctly, including the exclusive-end boundary.
5. `page_location` gives UNVERIFIABLE, and an unknown type gives UNVERIFIABLE without raising.
6. A missing required field raises `ValueError`.
7. `accumulate` over a replayed event list (text_delta, citations_delta, citations_delta, stop) equals the equivalent non-streaming block.
8. `uncited_text_blocks` flags a text block with no `citations`.
9. A mutation check: breaking the slice off-by-one (inclusive end) makes at least one test fail. Include it as a test that runs the verifier against a deliberately wrong reference.

Live (optional, flagged as billed, a few cents at most): all citations MATCH on the real response. The result settles the open question below and goes into `knowledge/citations.md`.

## Open questions
- Is `cited_text` always byte-identical to `doc[start:end]` for plain text (whitespace, trailing space after a sentence, as in the docs' `"The grass is green. "` example)? The live run will answer this.
- For `content_block_location`, is `cited_text` the plain concatenation of the blocks with no separator? Docs do not say.
- `search_result_location` and web-search citations have different fields and were not read. Left to a follow-up.
- Whether newer models (`claude-sonnet-5-5`) cite more or less often than Haiku 4.5. Not measured.
