# Multi-tool agent with a typed tool registry

## Question

What's the right way to run a Claude agent with *multiple* tools where each
tool's schema comes from real Python type hints instead of hand-written JSON
Schema — and how does that differ from the hand-rolled single-tool loop already
in `examples/minimal-agent-loop/`?

## Findings

### The SDK ships exactly this: `@beta_tool` + `client.beta.messages.tool_runner`

The `tool-use-loop` knowledge note already flagged this ("the SDK's Tool Runner
automates this whole loop — use it in real apps"). This cycle verified the
actual mechanism directly against the installed package, not just docs:

- Confirmed by installing `anthropic==0.120.0` in a scratch venv (2026-07-28,
  latest on PyPI as of today) and reading the source under
  `anthropic/lib/tools/_beta_functions.py` and `_beta_runner.py` — these are
  primary-source facts, not blog paraphrases.
- `anthropic.beta_tool` (sync) / `anthropic.beta_async_tool` (async) are
  decorators that turn a plain typed function into a `BetaFunctionTool`:
  - `name` = function name (overridable).
  - `description` = parsed from the docstring's short+long description.
  - `input_schema` = generated by feeding the function through
    `pydantic.TypeAdapter` + a custom `GenerateJsonSchema` that also pulls
    per-argument descriptions out of a Google-style `Args:` docstring block.
  - **Requires Pydantic v2** — raises `RuntimeError` under Pydantic v1.
  - Calling `.call(input_dict)` runs `pydantic.validate_call(func)(**input_dict)`;
    a bad type or missing required key raises `ValueError("Invalid arguments
    for function <name>")` wrapping the underlying `pydantic.ValidationError`.
    Verified directly: valid input returns the correct value, a wrong-typed
    field and a missing required field both raise `ValueError`.
- `client.beta.messages.tool_runner(model=, max_tokens=, tools=[...],
  messages=[...], max_iterations=N)` returns a `BetaToolRunner` (iterator).
  Each iteration yields one `ParsedBetaMessage` (a full turn — could contain
  `tool_use` blocks or the final answer); `.until_done()` drains it and returns
  the last message. Construction does **no** network call — only iterating (or
  calling `.until_done()`) does, verified by instantiating a runner against a
  fake API key without it raising.
- The runner's internal dispatch (in `_tool_dispatch.py`, private —
  `tool_registry()` there is not exported from `anthropic.lib.tools.__all__`)
  indexes tools by `.name` in a plain dict. An unknown tool name or a tool
  exception is **caught** and turned into a `tool_result` with `is_error: true`
  (verified by reading `_generate_tool_call_response`) — the loop itself never
  crashes on a bad or failing tool call. A tool can raise `anthropic.ToolError`
  to control the exact structured content returned instead of `repr(exc)`.
- **Gotcha, confirmed in source**: `max_iterations` defaults to `None`, and
  `_should_stop()` only stops early when it's set — i.e. **unbounded by
  default**, same failure mode the hand-rolled loop's `max_turns` guards
  against. Always pass `max_iterations=` explicitly.
- `client.beta.messages.tool_runner` lives under the **beta** namespace
  (`client.beta.messages`, not `client.messages`) — this is still beta as of
  today, first shipped per the SDK's public discussion in
  [`anthropics/anthropic-sdk-python` discussion #1036](https://github.com/anthropics/anthropic-sdk-python/discussions/1036)
  (posted 2025-09-18, SDK v0.68.0). That discussion also lists production pain
  points (no bounded retries, no parallel-execution flag, no lifecycle hooks) —
  worth flagging as "stale-ish" community commentary since some has since been
  addressed (`max_iterations` now exists; `parallel_execution` / lifecycle
  hooks still don't, per the 0.120.0 source read today).
- The `claude-api` skill's own docs mirror
  ([`skills/claude-api/python/claude-api/tool-use.md`](https://github.com/anthropics/skills/blob/main/skills/claude-api/python/claude-api/tool-use.md),
  fetched 2026-07-28, references 2025-2026-era server tools) documents the
  identical `@beta_tool` + `tool_runner` pattern as the *recommended* way to
  define tools in Python — this is not a fringe pattern.

### What "typed tool registry" concretely buys you

Compared to the hand-written `TOOLS` (list of raw JSON-Schema dicts) +
`TOOL_FUNCTIONS` (name→lambda dict) in `minimal-agent-loop/agent.py`:

- The JSON Schema is generated from the function's real type hints, so a typo
  in a hand-written schema (wrong required field, wrong type keyword) can't
  drift from what the function actually accepts.
- Bad tool-call input from the model is rejected by Pydantic *before* your tool
  body runs, with a clear error surfaced back to the model as a `tool_result`
  — free input validation, not something the hand-rolled loop has today.
- A "registry" is still just `{tool.name: tool for tool in TOOLS}` — the SDK
  doesn't force any heavier abstraction, so this stays a small, inspectable
  dict, consistent with this repo's "narrow surface, no magic config object"
  preference.

### Verified example (ran locally, 2026-07-28, offline — no network)

```python
from anthropic import beta_tool

@beta_tool
def word_count(text: str) -> str:
    """Count words in a string.

    Args:
        text: The text to count words in.
    """
    return str(len(text.split()))

word_count.name          # "word_count"
word_count.description   # "Count words in a string."
word_count.input_schema  # {"type": "object", "properties": {"text": {"type":
                          #  "string", "description": "The text to count words
                          #  in.", "title": "Text"}}, "required": ["text"],
                          #  "additionalProperties": false}
word_count.call({"text": "hello world foo"})  # "3"
word_count.call({"text": 123})                # raises ValueError
word_count.call({})                           # raises ValueError (missing "text")
```

This schema generation and validation is **pure, local, offline** — no API key
or network needed to exercise it, which matters for today's build proposal.

## Build proposal

New example: **`examples/typed-tool-registry/`**, sibling to
`examples/minimal-agent-loop/`, building directly on it.

**Shape:**

- `agent.py`
  - Three small, deterministic `@beta_tool`-decorated functions covering two
    different JSON Schema types so schema generation is visibly doing real
    work:
    - `word_count(text: str) -> str`
    - `reverse_text(text: str) -> str`
    - `is_prime(n: int) -> str`
  - `TOOLS = [word_count, reverse_text, is_prime]` and an explicit
    `TOOL_REGISTRY = {t.name: t for t in TOOLS}` — a plain dict, not a new
    abstraction.
  - `run_agent(client, user_message, *, max_iterations=8) -> str` that calls
    `client.beta.messages.tool_runner(model=MODEL, max_tokens=1024,
    tools=TOOLS, messages=[{"role": "user", "content": user_message}],
    max_iterations=max_iterations).until_done()` and returns the final text.
    `max_iterations` is always passed explicitly (see gotcha above).
  - `main()` follows the same pattern as `minimal-agent-loop/agent.py`: if
    `ANTHROPIC_API_KEY` isn't set, print a one-line note and exit 0 instead of
    crashing; otherwise ask something that needs at least two of the three
    tools (e.g. "Is 91 prime? Also reverse the word 'agent' and count the
    words in 'the quick brown fox'.") and print the answer.
  - Model id: reuse the existing `MODEL = "claude-haiku-4-5"` constant, per
    `knowledge/anthropic-models.md`.
- `test_agent.py` — fully offline, no fake client needed because schema
  generation and validation are real local code, not something to mock:
  1. For each tool in `TOOLS`: `.name` matches the function name, `.description`
     is non-empty, `.input_schema["type"] == "object"`, `.input_schema["required"]`
     lists exactly its parameters, and the JSON-Schema `type` for each property
     matches the Python hint (`"string"` for `text: str`, `"integer"` for `n: int`).
  2. `TOOL_REGISTRY` has exactly 3 entries and `TOOL_REGISTRY["is_prime"] is is_prime`
     (identity, not just equality).
  3. Each tool's `.call(...)` returns the correct value for a known input
     (`word_count` on a 4-word string, `reverse_text` on a known string,
     `is_prime` on a known prime and a known composite).
  4. Each tool's `.call(...)` raises `ValueError` on a wrong-typed argument
     (e.g. `is_prime.call({"n": "seven"})`) and on a missing required argument.
- `requirements.txt` — `anthropic>=0.120.0` (now needed for the self-test too,
  since it imports `anthropic.beta_tool` directly — unlike
  `minimal-agent-loop`'s stdlib-only offline test; call this out in the README).
- `README.md` — same shape as `minimal-agent-loop/README.md`: what's here, how
  to run the self-test, how to run it live, and one paragraph on how this
  differs from the hand-rolled loop (link back to this note and to
  `minimal-agent-loop/`).

**"It works" means:** `python test_agent.py` (after `pip install -r
requirements.txt`, no API key, no network) prints an all-`ok` summary covering
schema shape, registry lookup, correct-input results, and rejected-bad-input
for all three tools; `python agent.py` with `ANTHROPIC_API_KEY` set makes a
real multi-tool call and prints a final answer that correctly used at least
two of the three tools.

**Explicitly out of scope for today** (leave for later backlog items):
streaming (`BetaStreamingToolRunner`), async tools (`beta_async_tool`),
parallel tool execution, `ToolError` for custom structured errors, and
`client.beta.sessions` / MCP tool conversion.

## Open questions

- Whether `client.beta.messages.tool_runner` requires an explicit `betas=[...]`
  header today or the SDK adds it automatically — the source shows an internal
  `stainless_helper_header` merged into `extra_headers` automatically, but I
  did not make a real network call to confirm no additional beta flag is
  needed. If the live run 400s on a missing beta header, that's the first
  thing to check.
- Whether `tool_runner` (non-beta, under plain `client.messages`) exists or is
  planned — as of `anthropic==0.120.0` today it's beta-only
  (`client.beta.messages.tool_runner`); did not find any non-beta variant.
- The GitHub discussion's "requested features" (parallel execution flag,
  lifecycle hooks, `run_until`) may or may not have shipped since Sept 2025 —
  I confirmed `max_iterations` now exists but did not exhaustively check the
  rest against the 0.120.0 source; treat anything from that discussion not
  independently verified above as unconfirmed.
