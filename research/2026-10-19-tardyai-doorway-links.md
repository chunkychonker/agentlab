# TardyAI milestone 6: room routes go through doorways

Date: 2026-10-19. Mode: external:tardyai (kushsarora/TardyAI). Checkout `/Users/steeb/agentlab-work/tardyai` at 3c086d5 (main, includes #1-#5). No web research: this is a pure data/generator milestone, so the sources are the checkout and the plan PNGs.

## Question

How do we make every room link and the one hallway link enter through the drawn doorway gap, so `checks/walkability.py` (which now counts wall crossings) passes on main, without hand-editing JSON?

## Findings

1. **Measured state on main.** `python3 -I projects/tardyai/checks/walkability.py pkgbc231600` prints 62 violations: 61 `door -- room` links (L1 12, L2 about 24, L3 about 25) and the hallway link `n-f3-n1250 -- n-f3-d3210`. Counts per link range from 1 to 5 crossings (3163 has 5, 1425/3337/3344/2020D have 4). One crossing means the door is on the wrong side of a single wall. 3+ means the room node sits deep in a suite and the straight line cuts several partitions. No other violation kind remains (no corridor-blocked or over-15 m edges).
2. **Why they fail (from `tools/build_graph.py`).** The door node is the orthogonal projection of the room's label point (or its `door=` hint) onto the nearest corridor segment. It is therefore only ever on a corridor line, directly "below" the label, and the room edge is a straight line door -> label. Real doors are gaps in the wall, often angled corner doors (1280), so the straight line goes through a wall next to the gap. `RoomRow.door` today only chooses which segment to project onto; it cannot place the door.
3. **Two independent knobs fix a crossing.** (a) Where the door node is (must be in the corridor in front of the gap); (b) where the room node is (the label point is just inside the room; moving it a few px inward from the gap makes the final segment pass straight through the opening). Room node ids and `Waypoint` ids must stay; moving the room node's x/y changes the annotated plan marker only, regenerated by `build_waypoints.py`.
4. **The generator cannot express an off-corridor door today.** It splits a corridor segment at the projection foot; the door always has `hallway` edges only to its two segment neighbours. A door in front of a gap that is not on a corridor centreline needs a short `hallway` stub from the door to a corridor node or a foot node. The spec for the milestone says exactly that ("connect each door node to the nearest hallway node with a link that stays in the corridor"). Stub edges are corridor edges for the checker (>= 90% open, no wall crossings, 2 m endpoint margin), so the stub must itself be in open floor.
5. **No Pillow on the default python.** `/opt/homebrew/bin/python3` has no PIL/numpy; an earlier note records `/usr/local/bin/python3` has Pillow. `build_graph.py` is stdlib-only and must stay so. For a door finder, write a stdlib PNG decode (zlib + unfilter, like agentlab's `checks/png_rgb.py`, which the target must not import) or run it with the Pillow python as a dev-only aid. The `verify.sh` gate stays the oracle either way.
6. **Hot/protected check.** The work lives in `tools/grainger_corridors.py`, `tools/build_graph.py`, regenerated `data/MapNode`, `data/NavEdge`, `data/Waypoint`, `data/AnnotatedPlan`, annotated PNGs, tests under `test/node/`, README node/edge counts. None are in the protected or hot list. README.md IS hot: do not update the "75 nodes, 156 edges"-style sentence there (note it in the PR body instead). Do not touch `RoomFinder.*`, `*.c3typ` with new fields, or UI.
7. **Test pins to keep green.** `router.test.js` pins `n-f1-stair-w`, `n-f1-elev-e`, `n-f3-r3335`, West Entrance, and a 150-210 s ETA for West Entrance -> 3335 in 2 legs. `steps.test.js` has geometry-dependent fixtures: changing 3335's door placement changes the final step ("3335 is on your left/right") and seconds; update expectations and say so in the PR body per changed expectation. `rooms.test.js` requires every printed room reachable (and `unmapped-rooms.json` unchanged). Room Finder python tests (`test_room_finder.py`) use seed data, so rerun them; the 1310 -> 1170 oracle compares to the real router so it self-heals.

## Build proposal

Covers milestone 6 only (doorway links). One theme: the generator learns explicit doorways; the data is regenerated; the checker passes.

**Intent.** Every room link and the n1250--d3210 hallway link enters through the real wall opening, so `walkability.py` reports zero wall crossings and `VERIFY: PASS`. Out of scope: new rooms, the 11 `not_mapped` suite rooms, router/UI/Room Finder code, gate rule changes, README (hot).

**Behavioral spec.**
- Inputs: `FLOOR_PLANS` in `tools/grainger_corridors.py`, extended per room. Outputs: `data/MapNode`, `NavEdge`, `Waypoint`, `AnnotatedPlan` JSON plus annotated PNGs via `build_waypoints.py`.
- New optional `RoomRow` field `doors: tuple[Point, ...]` (default empty = today's behaviour, so unchanged rooms keep their ids and positions). Each point is a door-node position in the corridor in front of a gap. First door keeps id `d<number>`; extra doors (rooms with two openings) get `d<number>-2`, ... (the router needs no change; the room has one `room` node linked to each of its doors).
- For each explicit door the generator finds the nearest corridor segment, inserts a foot node only if the door is not already within `DOOR_MIN_GAP_PX` of the segment; otherwise it splits the segment as now. If the door is off the centreline, add a `hallway` edge from the door to the foot (id local `f<number>`), kept <= a named constant (suggest 8 m).
- `RoomRow.x, y` may be moved inward so door -> room is a straight segment through the gap. Room edge stays <= 15 m (`MAX_ROOM_EDGE_METERS`), still the only link a room has besides its other doors.
- Fix `n-f3-n1250 -- n-f3-d3210`: the 3210 door is projected onto a segment whose neighbour link crosses a wall; supply a door and, if needed, split/redraw the corridor chain so the hallway chain n1250 -> d3210 does not cross.
- Failure modes (all `ValueError` naming the room, raised before any file is written): door more than the stub cap from any corridor; two doors closer than `DOOR_MIN_GAP_PX`; stub or room edge over caps; explicit door for an unknown or `not_mapped` room.
- Invariants: node ids that exist today survive (every `n-f*-r<num>`, connector ids, `d<num>`); `connectorKey`s unchanged; seconds computed by the existing `_edge_rows`; generator output deterministic and idempotent (running twice yields identical files).

**Interfaces.**
```python
class RoomRow(NamedTuple):
    number: str; x: float; y: float
    name: str | None = None
    door: Point | None = None            # existing: segment-choice hint
    aliases: str | None = None
    doors: tuple[Point, ...] = ()        # NEW: explicit doorway positions
# build_graph.py
MAX_DOOR_STUB_METERS: float = 8.0
def place_doors(room: RoomRow, segments, coords) -> list[tuple[str, Point, int]]: ...
```
Plus a dev-only `tools/find_doorways.py` (optional, stdlib): for each room the checker flags, scan open pixels within ~8 m of the corridor and print candidate `doors=` points whose door -> room line has zero wall crossings, shortest first. It only suggests; the builder eyeballs crops and pastes values into `grainger_corridors.py`, so the source of truth stays the corridors file.

**Method for the builder.** (1) Run walkability to get the 62-item list. (2) Crop each failing room from `floor_p{1,2,3}.png` (look at the picture; the hard cases are the 3+ crossing ones: 1210, 1290A, 1425, 2020D/H, 3161/3163/3165, 3337, 3344). (3) Put `doors=` and adjust `x,y`. (4) Regenerate with `build_graph.py` then `build_waypoints.py` (use the Pillow python), rerun verify until zero crossings. Many single-crossing rooms share a pattern (door projected onto the wrong side of the wall): fix by pattern per corridor run, not one at a time. If a room cannot pass without a wall rule change, list it in the PR body and in `unmapped-rooms.json` only with a decisions-log note; prefer to fix it.

**Acceptance criteria.**
1. `bash projects/tardyai/verify.sh <checkout>` prints `VERIFY: PASS`, including "routes stay in corridors" (0 wall crossings, incl. n1250--d3210) and "seed data integrity".
2. New node test (`test/node/doorways.test.js`, `node --test`, stdlib only): generator unit cases via a tiny python call are not possible from node, so assert on seed data instead: every `room`/`restroom` node has >= 1 `door` edge, every door edge <= 15 m, node ids `n-f1-r1280`, `n-f1-r1140`, `n-f1-r1270`, `n-f3-r3335` exist, and the 1310 -> 1270, 1310 -> 1280 and West Entrance -> 3335 routes end with a door-edge leg whose last polyline point is the room node.
3. A python unittest for the generator (`test/py/test_build_graph_doors.py`, run by the existing py step, stdlib): a synthetic FloorPlan with one explicit door yields the expected nodes/edges; an unreachable door (beyond stub cap) raises `ValueError` naming the room; running `build_floor` twice gives equal output.
4. `rooms.test.js` (all printed rooms reachable) and `router.test.js` pass unchanged; `steps.test.js` expectations that changed are listed in the PR body, one line each.
5. PR attaches overlay crops of 1280, 1140 and 1270 (route drawn over the plan) showing the last segment passing through the opening. The checklist adds "Re-provision in Studio to reload seed data".

**Risk.** Biggest: effort across ~60 rooms by eye. The mitigation is the pattern grouping, `find_doorways.py` suggestions, and the checker as an automatic oracle (no sampled crossing = done). Failure domain: seed data only; a bad door breaks routes to that room, caught by `rooms.test.js`.
