# Typed tool registry (`@beta_tool` + `tool_runner`)

A multi-tool Claude agent where every tool's JSON Schema comes from real
Python type hints and a docstring, not a hand-written dict - and where the
tool-use loop itself is the SDK's `client.beta.messages.tool_runner`, not a
loop we write by hand.

From the research note:
[`research/2026-07-28-typed-tool-registry.md`](../../research/2026-07-28-typed-tool-registry.md).

## What's here

| File | What it is |
|------|-----------|
| `agent.py` | Three `@beta_tool`-decorated functions, `TOOL_REGISTRY` (a plain `{name: tool}` dict), and `run_agent()` which drives `client.beta.messages.tool_runner(...).until_done()`. |
| `test_agent.py` | Offline self-test: schema shape, registry lookup, correct-input results and rejected-bad-input for all three tools, plus `run_agent`'s text-join on a clean finish and its `RuntimeError` on `max_iterations`. No key, no network. |
| `requirements.txt` | `anthropic>=0.120.0` - needed for **both** the live run and the self-test (see below). |

The three tools are plain, deterministic Python functions covering two
different JSON-Schema types so schema generation is visibly doing real work:

- `word_count(text: str) -> str`
- `reverse_text(text: str) -> str`
- `is_prime(n: int) -> str`

`@beta_tool` turns each into a `BetaFunctionTool`: `.name` is the function
name, `.description` comes from the docstring, and `.input_schema` is
generated from the type hints via Pydantic (`text: str` -> JSON type
`"string"`, `n: int` -> `"integer"`), with per-argument descriptions pulled
from the `Args:` block. `.call(input_dict)` validates the input with Pydantic
*before* the function body runs, and raises `ValueError` on a wrong-typed or
missing argument instead of letting bad input reach the tool.

## Run the self-test (no API key needed, but does need `anthropic` installed)

```bash
cd examples/typed-tool-registry
pip install -r requirements.txt
python test_agent.py
```

Expected output:

```
ok  each tool's schema (name/description/type/required) matches its type hints
ok  TOOL_REGISTRY has exactly 3 entries, keyed by name with true identity
ok  each tool's .call(...) returns the correct value for a known input
ok  each tool's .call(...) raises ValueError on wrong-typed or missing arguments
ok  run_agent joins the final text blocks on a clean finish
ok  run_agent raises RuntimeError instead of returning '' on max_iterations

All 6 self-tests passed.
```

Verifiable, not hand-copied:
[`examples/readme-transcript-check`](../readme-transcript-check/) checks this
block against the real thing —
`python3 check_transcript.py ../typed-tool-registry -- python3 test_agent.py`.
This transcript claimed "All 4" from PR #2 (2026-07-29) until the 2026-08-10
health check flagged it; the checker did not find that drift, it is what now
keeps it from coming back. Run it from this example's venv — a bare interpreter
without `anthropic` reports `UNRUNNABLE`, not `MATCH`, which is the distinction
the checker exists to draw.

This differs from `minimal-agent-loop`'s self-test: there, the tool
(`calculator`) is stdlib-only and the loop mechanics are exercised against a
scripted fake client, so the test needs no dependency at all. Here, schema
generation and input validation are the thing under test, and both are real,
pure, local `anthropic` code - so the test imports the real package and
exercises the real `BetaFunctionTool` objects. No fake client is needed
because nothing here makes a network call.

## Run it live (needs a key)

```bash
pip install -r requirements.txt
export ANTHROPIC_API_KEY=sk-ant-...
python agent.py
```

It asks *"Is 91 prime? Also reverse the word 'agent' and count the words in
'the quick brown fox'."* - a question that needs at least two of the three
tools - and prints Claude's final answer. Without `ANTHROPIC_API_KEY` set,
`agent.py` prints a one-line note and exits 0, same as `minimal-agent-loop`.

Model id is the constant `MODEL` at the top of `agent.py` (default
`claude-haiku-4-5`). See
[`knowledge/anthropic-models.md`](../../knowledge/anthropic-models.md).

## How this differs from `minimal-agent-loop/`

[`minimal-agent-loop/`](../minimal-agent-loop/) hand-writes one tool's JSON
Schema as a dict, dispatches it through a `{name: lambda}` map, and drives the
turn-by-turn `messages.create` loop itself (echo the assistant turn, run the
tool, append a `tool_result`, repeat until `stop_reason != "tool_use"`).

This example keeps the same shape - a list of tools plus a `{name: tool}`
registry dict, nothing heavier - but:

- **Schema comes from the function**, generated by `@beta_tool` from real type
  hints, instead of being hand-written and able to silently drift from what
  the function actually accepts.
- **Bad tool input never reaches the tool body.** Pydantic validates it first
  and raises `ValueError`, which is exactly what `test_agent.py`'s rejection
  tests check.
- **The loop itself is the SDK's, not ours.**
  `client.beta.messages.tool_runner(...).until_done()` replaces the manual
  `while` loop. It still needs an explicit turn cap - `max_iterations`
  defaults to `None` (unbounded) - so `run_agent()` always passes it, the same
  discipline `minimal-agent-loop`'s `max_turns` enforces by hand.

`client.beta.messages.tool_runner` lives under the **beta** namespace as of
`anthropic==0.120.0` (2026-07-28) - see the research note for what that
means and what's still unconfirmed against a live API call.

## Explicitly out of scope

Streaming (`BetaStreamingToolRunner`), async tools (`beta_async_tool`),
parallel tool execution, `ToolError` for custom structured error content, and
`client.beta.sessions` / MCP tool conversion - separate backlog items.
